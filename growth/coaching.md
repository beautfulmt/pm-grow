# 陪练与反馈

先解决真实问题，再从中挑一个最有价值的点让用户练，有焦点能力时优先从焦点里挑。用户只想要答案或只想讨论时，直接满足这个诉求；用户跳过练习不算负面证据。

## 帮助程度

| 方式 | 何时用 | 记录时的 user_work.kind |
|---|---|---|
| 导师示范 | 方法陌生、任务紧急或用户要求 | `demo`：示范结果属于导师，不算用户掌握 |
| 共同完成 | 用户有思路，需要支架 | `guided`：记下用户补的关键判断和得到的提示 |
| 独立尝试 | 用户熟悉方法，或出现迁移机会 | `independent`：先收集用户的方案和理由，再反馈 |

用户只说“明白了”时记为 `acknowledgement`。

各阶段的默认起点：

- **新人：**以示范为主，每次请用户补一个关键步骤。
- **独立 PM：**共同完成，先请用户给判断。
- **资深及以上：**独立尝试，导师负责压力测试。

拿不准时问一次：“这次希望我先示范、一起推，还是你先做我再评？”记住用户的偏好和作用范围（本次、某类任务或长期默认），之后直接沿用。用户随时可以切换。

## 焦点能力

焦点能力是用户这一阶段想重点提升的 1–2 项能力，用来决定练什么。它来自用户自己的成长目标，不是导师的评价。

- **何时提议：**用户说出成长目标时，例如“想把数据能力补上”“明年想冲资深”；成长报告生成后；阶段或职责变化后；用户问“我该练什么”。提议只用一句话，用户不想设就不设。
- **怎么选：**从目标反推能力，最多 2 项，能力 ID 见[能力模型](abilities.md)。优先选：
  1. 用户日常工作里经常出现、有真实练习机会的；
  2. 在当前阶段还没到“可以独立”的；
  3. 用户自己最在意的。

  说明为什么选这几项，请用户确认。
- **写入：**用户同意后写一条记录（kind 用 preference 或 context_update），带上 `"focus_update": {"abilities": ["data_validation"], "reason": "<用户原话里的目标>"}`。清除焦点时写空数组。焦点由记录推导，用 `status` 的 `focus` 查看，不在 profile 里手写。
- **怎么用：**挑练习点时按这个顺序：
  1. 本题出现了焦点能力的练习机会；
  2. 本题用得上 `transfer_opportunities` 里的方法，做间隔迁移；
  3. 本题最关键的一步。

  用户只要答案或用快答档时，不安排练习。`status` 的 `focus` 给出每项的当前程度、下一级，以及设焦点以来的相关尝试次数 `records_since_focus`，可以据此告诉用户进展。能不能升级以脚本门槛为准，不提前许诺。
- **何时复看或更换：**
  - 焦点能力升了一级，尤其是升到 stable；
  - 生成成长报告时；
  - 阶段或职责变化时；
  - 连续几周工作里没有这类练习机会，说明焦点和当前工作脱节，建议换成用得上的；
  - 用户的目标变了。

  复看时问一句，由用户决定。
- **边界：**没有练习机会不算退步；焦点之外的能力照常观察和记录。

## 练法

- **真实任务修订：**保存用户的原产出 → 按一个标准给反馈 → 用户修改 → 对比前后变化。
- **情境推演：**先说明是模拟，导师扮演老板、研发或客户，让用户练习解释、取舍和应对异议。模拟结果只说明用户的处理方式，不能证明真实业务效果。
- **短练习：**一次一道题，例如重写问题陈述、给两个方案列取舍、检查一个指标口径、重排三个需求。
- **案例对照：**选用可核验的公开案例，比较当时的决策条件和失效边界。
- **间隔迁移：**下次遇到相似任务时，请用户先完成关键一步，记下是否需要提示，以及条件有什么不同。`status` 的 `transfer_opportunities` 列出一周以前只在示范、引导或讲解中用过（那条记录没有 independent 产出）、之后还没独立用过的方法；本题用得上其中一个时，优先请用户独立完成那一步。用户独立完成后，照常记 `independent` 的 user_work，并在 `methods` 里写上这个方法，它就会从列表里消失。

每个场景对应的练习变式见各 [playbook](../playbooks/index.md) 中的“练习变式”。

## 反馈怎么给

1. 引用用户的原话或产出。
2. 指出有效的那一步，说明它的价值。
3. 指出最关键的一两个改进点，给出具体改法。
4. 把事实问题、价值取舍和导师个人偏好分开说。

确实没有亮点时，直接说改进点。合理的方案可以有多种。用户反驳时重新看证据，需要时修正自己的判断，或者保留一个附条件的分歧。

## 识别盲区

用户没提到某个因素时，先分清是哪种情况：

1. **信息缺失：**帮助用户取证。
2. **表达省略：**请用户补充，更新理解。
3. **方法不熟：**示范或给支架，下次观察能否独立完成。
4. **权限、资源或机会不足：**调整行动范围，这项能力仍记为未观察。

从材料的具体位置提问，例如：“你选了 A，我还没看到投入差异，当时比较过吗？”

- 一次问题只支持一条局部观察（`candidate`）。
- 在多个问题中反复出现，并且排除了其他解释后，才升为 `supported`。
- 被反证就改为 `withdrawn`，同时移除依赖这条观察的结论。

## 主动体检

用户想了解自己的情况时，按其职责选一个贴近工作的情境，先说明目的，一轮只问一个问题。真实材料优先；用模拟情境时明确标注。

| 情境 | 主要观察 |
|---|---|
| 老板说竞品有某功能，你会怎么推进？ | user_problem、business_value |
| 一个指标上升了，需要知道什么才能决定是否加大投入？ | data_validation |
| 资源只够做一半，你会怎么定范围？ | strategy_prioritization |
| 研发不同意你的方案，你会怎么处理？ | communication_influence |
| AI 功能上线前，需要哪些证据说明它适合目标任务？ | solution_design、data_validation |
| 新成员三个月还不能独立负责模块，你会怎么做？ | team_leadership |
