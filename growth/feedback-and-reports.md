# 反问、成长告知与成长报告

这三件事构成“解决问题之后”的成长闭环：

- **反问**：确认问题是否真的解决了。
- **成长告知**：让用户清楚自己哪里进步了。
- **成长报告**：在合适的时候把一段时间的收获整理成可以留存的页面。

## 1. 阶段性反问

### 会话内的三个检查点

| 时机 | 反问 | 作用 |
|---|---|---|
| 问题定义后 | “我们把问题定为 X，这是你真正要解决的吗？” | 防止解错题 |
| 选定方案后 | “按这个方案做，最初的问题能解决到什么程度？还剩什么？” | 检查方案与问题是否对齐 |
| 行动或上线后 | “结果怎么样？问题解决了吗？” | 拿到结果，更新问题状态 |

每个场景的具体问法见对应的 [playbook](../playbooks/index.md)。简单问题可以把检查点合成一句话，保持对话节奏。

### 跨会话回访

1. **登记回访点。**给出方案或约定行动时，在记录的 `problem.check_back` 里写下回访时机和要问的问题。回访时机可以是日期，也可以是条件，按问题性质定：
   - 上线类：上线后一到两周。
   - 沟通类：对应会议之后。
   - 探索类：用户下次提到这个话题时。
2. **开场提问。**每次开场运行 `status`。`follow_ups_due` 先列到期项，逾期最久的排在前面；有到期回访时，先用一句话问：“上次说的 X，现在怎么样了？”用户可以跳过或改天再聊。精简版最多列 5 个到期项和 5 个条件项，总数见 `counts`，需要全部时加 `--full`。
3. **按条件回访。**`condition_pending`（只登记了条件、没有日期）的回访，等用户提到相关话题时再问。
4. **终态后自动失效。**问题在登记回访之后被写成 solved、dropped 或 closed，这个回访就不再出现，不必再问。已经解决、但还想过一段时间确认效果时，在写终态的同一条或之后的记录里重新登记 `check_back`。
5. **长期没动静的问题。**`stale_problems` 列出 30 天没有新记录、也没有未来回访日期的未结问题，最久的排在前面。每次会话最多问一个，放在到期回访之后：“X 还要继续跟吗？”用户正急着处理新问题时，放到本轮收尾再问；同一个问题已经作为到期回访问过时，不再重复问。按回答写一条 `follow_up`：不跟了写 dropped，结束但结果未核实写 closed，还要跟就写下一步。写过之后它就不再出现；用户说先放着，也照样记一条，30 天内不再问。
6. **写回状态。**按用户的回答写一条 `follow_up` 记录，更新 `problem.status` 和 `outcome`：

   | 状态 | 含义 |
   |---|---|
   | solved | 已解决 |
   | partial | 部分解决 |
   | blocked | 受阻 |
   | dropped | 放弃 |
   | closed | 已结束但结果未核实 |

7. **一起复盘。**问题没解决时，和用户一起看卡在问题定义、方案还是执行。这是很好的复盘材料，对应 learning_transfer 能力。

## 2. 两级告知能力提升

每个包含用户本人尝试的实质任务结束时，按下面的格式告知：

```text
【本次表现】
你先把“老板要签到”还原成“7 日留存从 32% 降到 25%”，这是问题界定的关键一步。

【能力变化】
用户洞察与问题界定：需要支持 → 可以独立
依据：9/28 的报表需求需要我提示 3 次，这次和 10/12 的推荐位问题你都独立拆出了口径和人群。

【仍在练】
选验证方式时，还会先想到做功能。下次先想一想：有没有不做功能也能验证的办法？
```

- **【本次表现】**引用用户自己的原话或产出，对照用户当前阶段的[锚点](stages.md)，说清做到了哪一步、为什么这一步关键。这次以导师示范为主时，就说明“这次以我示范为主，下次你可以先试 X”。
- **【能力变化】**只在本次记录了 `ability_updates` 时出现。升级门槛由脚本校验，见[证据与记录](../reference/evidence-and-records.md)。门槛满足时，直接、明确地告诉用户“提升了”。
- **【仍在练】**写成可以练的下一步。“数据能力不足”这类笼统说法换成具体动作和下一次的练习机会。
- **跨阶段判断：**某项能力要升到 stable，或按表现建议升阶时，写入记录之前先自动委派 growth-reviewer 独立复核证据，并告诉用户。结论写进记录的 `review`；没有委派工具时由主导师自查，写 `self_check` 并如实说明。复核不支持时不升级，告诉用户还缺什么。见[多 Agent 协作](../reference/agents.md)。
- **用户不想练时：**用户只要答案、明确不想练或要求不记录时，最多给一句【本次表现】。

## 3. 成长报告 HTML

### 何时提议

`status` 返回的 `report.due` 为 true 时，等当前问题自然收尾，用一句话提议，例如：“最近两周你处理了 3 个问题，有两项能力有变化，要不要生成一份成长报告？”

`status` 会在 `report.reasons` 中给出触发原因：

- 上次报告之后，已有 3 个不同的问题包含用户本人尝试。
- 距上次报告超过 14 天，并且期间有新记录。
- 关键节点：一个问题解决或有了结果、出现能力升级，或标记了 milestone（上线、评审通过、述职等）。

另外，用户随时要求都可以生成。

- **自动模式：**`settings.report_mode` 为 `auto` 时，直接生成并告知用户。
- **用户暂缓：**运行 `report defer`。暂缓后只看之后写入的新记录：再出现 3 个含用户尝试的问题、出现新的关键节点，或者暂缓满 14 天且期间有新记录，才会再次提议。暂缓之后多一条普通记录，不会重新提议。
- **约定日期：**用户说“下个月再说”时，运行 `report defer --until <日期>`。这一天之前一律不提议；到了这一天，还没写进报告的记录会再次提议（原因代码 `until_reached`）。
- **时机：**用户正在处理紧急问题时，先把问题解决完。

`report.deferred`、`deferred_on`、`deferred_until` 显示当前的暂缓状态。生成一份报告后，暂缓状态自动清除。

### 报告内容

1. **最近学了什么、做了什么：**学到的方法，包括方法卡和它在本业务中的用法；完成的任务和用户的产出。
2. **遇到的问题和解决情况：**每个问题的处理方式、当前状态和结果；没解决的，写清卡在哪里。
3. **成长与欠缺：**用两级告知的格式写能力变化和依据；欠缺写成“仍在练”，附下一步。设了焦点能力时，这一节开头是“本期焦点”，列出每项焦点能力的当前程度、本期练到的次数和变化。结尾是“能力全景”：各项能力在当前阶段的程度，以及此前阶段已经达到的程度。换阶段后，新阶段的能力从“未观察”重新起步，此前的成绩不会消失。能力变化经过复核时，标出“经独立复核”或“主导师自查”。

附录包括：下一阶段的重点（结合[阶段路径](stages.md)中的升阶信号）和证据。`growth_summary` 可以对照焦点写本期进展，只写事实部分能支持的内容。

### 生成步骤

1. **汇总事实。**由脚本从记录中汇总：

   ```sh
   python3 <skill-dir>/scripts/pmgrow.py --data-dir <data-dir> report draft > <tmp>/report.json
   ```

2. **补写叙述。**导师补全 `narrative` 中的 headline、learned_summary、problems_summary、growth_summary、gaps、next_focus 和 message。只写事实部分能支持的内容；事实里没有体现的成长，不写进报告。没有可靠的欠缺依据时，`gaps` 保持空数组，说明仍待实际尝试后观察。
3. **生成页面。**

   ```sh
   python3 <skill-dir>/scripts/pmgrow.py --data-dir <data-dir> report build --input <tmp>/report.json
   ```

   页面写入 `reports/YYYY-MM-DD.html`，同时更新报告游标。
4. **检查交付。**有浏览器工具时打开页面检查，然后把绝对路径给用户；无法检查时如实说明。报告是给用户本人看的；内容涉及公司信息时，提醒用户分享前先检查一遍。

## 4. 平时的轻量收尾

还没到报告时机时，一个实质问题结束时按这次的目的收尾：

| 目的 | 收尾内容 |
|---|---|
| 探索 | 新的理解、不同的解释、仍未解决的问题 |
| 决策 | 取舍、下一步行动、回访点 |
| 练习 | 两级告知 |
