# PM 能力模型 v1

这是服务训练的工作模型。它综合现有实战分类与美国、中国互联网产品组织的公开资料，需持续由真实案例校准，不代表任何公司的职级或晋升标准。

## 八项底座

采用稳定英文 ID 记录证据，对用户展示中文名称。旧模型按名称迁移，旧编号 3 和 4 与当前顺序不同，禁止按序号直接继承评价。

| ID / 能力 | 可观察行为 | 任务与验证证据 |
|---|---|---|
| user_problem / 用户洞察与问题界定 | 分清现象、需求、原因和方案；联系具体用户与证据 | 从一条需求还原问题，比较用户原始定义与修改后的定义 |
| business_value / 业务与价值判断 | 说明用户收益、业务收益、价值链、成本与约束；区分事实和价值预期 | 为真实需求解释值得投入的条件，核对关键业务假设 |
| solution_design / 方案设计与技术判断 | 理解用户任务和机制，比较备选，覆盖体验、边界及可行性 | 方案对比、流程或原型，经相关方校准的技术与资源取舍 |
| data_validation / 数据分析与效果验证 | 检查口径、基线和数据质量，区分相关与因果，提出验证条件 | 对变化给出竞争解释，设计可执行的取证或验证办法 |
| strategy_prioritization / 策略取舍与规划 | 围绕目标排序、明确代价、安排节奏，按新证据调整 | 资源受限时重排真实需求，解释先后与停止条件 |
| delivery_risk / 交付推进与风险控制 | 识别依赖、决策点、风险和验收标准，持续跟进结果 | 项目阻塞分析、风险处置、验收和上线回看 |
| communication_influence / 沟通协作与影响力 | 面向相关方清楚表达判断，理解诉求，处理分歧与形成行动 | 评审模拟、实际沟通产出、反馈及后续决策 |
| learning_transfer / 复盘学习与方法迁移 | 修正原判断，识别条件与自身可改善部分，把方法用于新题 | 前后产出对比、解释变化、间隔后的新情境独立应用 |

### 区分相邻维度

业务价值判断看投入是否值得，策略规划看整体如何取舍。方案设计看机制与体验如何成立，交付推进看协作和风险如何被处理。结构化表达通常映射 communication_influence；若错误在产品机制或问题结构本身，再关联对应维度。一个现象可以关联多维，但不会因此增加独立案例数。

## 每项能力分别观察

| 状态 | 证据含义 | 合适的下一步 |
|---|---|---|
| 未观察 | 没有足够的本人行为材料 | 了解相关经历或提供轻量情境 |
| 需要支持 | 借助提示或示范能完成边界清楚的任务 | 保留支架，逐步减少提示 |
| 可以独立 | 能选择方法、解释取舍，完成任务闭环 | 换情境、提高约束或复杂度 |
| 复杂情境下稳定运用 | 在不同模糊或冲突情境中持续完成判断与调整 | 检查跨场景迁移与方法适用边界 |

比较时记录任务复杂度、独立程度、影响范围、证据来源和稳定性。一次成功可记录本次独立完成，不能据此宣称稳定掌握。没有承担某类工作的机会时保留未观察。

初中高自报帮助选择起点，同一人各维度可以不同。不给未评维度打零分、不平均为总分、不从单次表现推断整体职级。用户问整体水平时，给当前有证据的范围和不足，不把专家成长等同于带团队。

## 业务与职责叠加

按当前任务选用，不启动全科检查。业务知识如何获取见[知识获取](知识获取.md)。

- **B 端与平台：**业务流程、多角色诉求、复用边界、实施和使用价值。
- **C 端与增长：**用户任务、理解与操作成本、激活留存、试验与长期价值。
- **数据与 AI 产品：**数据质量、技术能力边界、评测、人机协作、成本和延迟。
- **行业：**用户关系、价值链、内容或服务质量、关键规则等；从实际业务取证，不能凭行业标签补全公司情况。
- **团队负责人：**目标与资源取舍、授权与责任、跨团队协作、反馈与成员培养。只评估用户自己的行为，避免据其描述给成员评级。

## 优先训练什么

优先选择影响当前任务、本人有机会实践、并能观察反馈的一个点。用户主动想练的主题可以直接纳入计划，不需要先证明有缺陷。反复模式需独立案例和反证检查，详见[档案与证据](档案与证据.md)。

## 参考边界

GitLab 的职业发展资料用于研究可观察行为与责任范围，SVPG 用于有针对性的辅导，腾讯资料用于专业与负责人发展路径和真实产品案例，TikTok 岗位用于具体业务任务示例。详细来源见[知识获取](知识获取.md)。公共部门岗位框架不作为本模型的基线。
