# 第一性原理解题

用来澄清目标、检验假设、推导选择和设计验证。这里提供可复用的判断步骤与关键依据，不要求展示冗长的内部分析过程。

## 六个检查点

| 检查点 | 应当厘清什么 | 对用户有用的交付 |
|---|---|---|
| 目标 | 谁的什么处境需要改变，用户价值与业务目标如何关联 | 问题定义、成功标准 |
| 事实 | 哪些可观察，来源是什么；哪些属于推断、偏好、经验 | 关键证据、未知和假设 |
| 约束 | 时间、资源、技术、权限中哪些固定，哪些可协调 | 现实可行范围 |
| 机制 | 问题可能怎样发生，预设功能依赖哪些因果假设 | 有证据支持的解释及竞争解释 |
| 选择 | 有哪些不同路径，维持现状或较小改动是否值得比较 | 推荐、代价、边界和未选理由 |
| 验证 | 什么观察支持或反驳关键判断，下一步最小行动是什么 | 取证或试验、继续调整停止条件 |

事实不足先走信息闸门。先前的建议、自报职级、行业惯例和“人性如此”都不能自动升级为事实。用户明确的价值选择应被尊重，并与可验证事实分开说明。不可擅自放松真实法律、预算或授权约束。

## 按题目调节深度

- **简单问题：**结论、关键依据、下一步即可，不要硬凑六个标题。
- **复杂决策：**展开会影响选择的证据、假设、机制、取舍和验证，避免堆方法名。
- **事实查询：**必要时查证并回答，第一性原理不代替获取事实。
- **情绪化或混乱叙述：**先帮助还原事件和当下诉求，再做分析，不急于反问动机或贴能力标签。

## 解题与教学同时发生

默认示范后逐步放手。解释一条本题最有价值的方法及它何时会失效。共同完成时让用户补一个关键步骤；独立尝试时先收集用户产出，再按相同标准反馈。用户急需答案时可以直接示范，不因此下调能力状态。

## 示例：用户提出“做签到来提高活跃”

先厘清要改变哪类用户的什么行为、当前中断发生在哪、有何证据。签到能够带来入口访问是一个假设；入口访问与用户完成核心任务之间还需验证。可能的方案包括减少任务摩擦、提供即时价值或增加提醒，是否适用取决于原因。给出选择前补齐决定性的上下文，验证时同时观察目标行为和对用户的成本。

不要预设签到一定有效或一定无效，也不能把一次问题里遗漏数据当作缺乏数据能力。
