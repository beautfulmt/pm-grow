# 档案、案例与证据

## 数据归属

数据目录按用户明确指定、环境变量 `PM_GROW_DATA_DIR`、`~/pm-grow-data/` 的顺序解析。一个目录服务一位学习者，Codex 和 Claude 可共用。不同学习者明确使用不同目录，不能把他人的案例并入默认个人画像。

第三方代问、仅交付制品、技能维护和用户明确不记录的场景不自动初始化个人档案。维护任务若明确授权修复已有档案，可在该范围内处理。

只有主导师读写当前学习者档案。受邀专家只能返回与本题有关的分析、证据和建议，由主导师核对归属与来源后整合，不能自行初始化或写入个人数据。本文描述的是允许记录时的操作流程，不改变用户“不记录”的选择。

## 文件分工

| 文件 | 用途 |
|---|---|
| profile.md | 实际职责、经验自报、当前关注点、帮助偏好、分维度快照 |
| business-context.md | 行业与公司业务事实、来源、日期、约束、未知与冲突 |
| events/<event-id>.json | 不可变日常事件，保留日期、原来源、本人贡献、帮助和更正关联 |
| growth-log.md | 人工追加记录与 events/ 的可重建摘要索引 |
| cases/<case-id>.json | 独立案例及用户尝试证据，作为阶段回顾计数来源 |
| abilities.json | 当前学习者扩展能力注册表，补充通用底座 |
| learning-plan.md | 当前练习主题、选题理由、下一步、待回访和知识沉淀邀请 |
| review-state.json | 已回顾案例、暂缓时证据指纹及回顾记录 |
| knowledge/handbook.json | 经确认纳入手册的专题知识源 |
| handbook.html | 经确认后生成的累计知识手册 |

初始化只补缺失文件，不覆盖已有记录。命令中的 `<skill-dir>` 替换为当前实际技能目录；Python 命令使用环境已有的 Python 3，Windows 可用 `py -3`。没有 Python 时可用宿主文件工具按同一案例规则人工核对，并说明未运行自动校验。

```sh
python3 <skill-dir>/scripts/state.py --data-dir <data-dir> init
python3 <skill-dir>/scripts/state.py --data-dir <data-dir> review-status
```

无文件工具时在会话内工作，交付可保存的摘要并说明无法跨会话可靠接续。用户请求不记录时不运行写入命令。

## 日常摘要与跨次接续

本人学习且允许记录时，一轮出现实质新信息就保存一个简短事件：问题理解变化、用户提出新的假设或选择、探索中的取舍、业务或职责变化、明确偏好、未决事项、下一步或纠错。方案尚未完成也可以保存。纯寒暄、重复确认和没有新增内容的重复解释不另记；不要逐条复制聊天。

日常事件用于恢复上下文，不自动成为能力证据。区分用户实际贡献、导师或专家提供的帮助、仍待核实的内容。只有模型给过的方案记在 `assistance`；用户说“理解了”不能写成独立产出。能力观察仍需回到原始用户材料并满足案例规则。

开始或接续任务时，先读取当前背景与计划，再取最近少量摘要；已知案例或上下文时加过滤，只展开本题相关的完整事件、案例和来源。核对旧约定是否仍适用，优先接上未决事项和下一步，避免重新询问已知信息。旧人工 Markdown 记录继续按标题、日期和来源定位读取，无须批量转换。

```sh
python3 <skill-dir>/scripts/memory.py --data-dir <data-dir> recent --limit 5
python3 <skill-dir>/scripts/memory.py --data-dir <data-dir> recent --limit 5 --case-id <case-id>
python3 <skill-dir>/scripts/memory.py --data-dir <data-dir> recent --limit 5 --context-ref <context-ref>
python3 <skill-dir>/scripts/memory.py --data-dir <data-dir> append-event --input <event.json>
python3 <skill-dir>/scripts/memory.py --data-dir <data-dir> rebuild-log
```

`recent` 是只读命令，目录不存在时返回空列表，不初始化档案。`events` 返回过滤后最新 N 条，按事件发生日期 `date`、同日写入时间 `recorded_at`、ID 升序；`related_events` 单独返回关联的原记录及更正链，使用相同顺序。关联补充不占 N 条限额，包含没有相同 case/context 标签的后续更正，不能只读原记录忽略更正。旧事件没有写入时间时保留原文件，同日排在有时间的事件之前，并按 ID 保持稳定顺序，无法还原其历史写入先后。`record_ref` 指向的旧记录需主导师按位置补读。

事件 schema 如下；`schema_version` 可省略，保存时补为 1。必填 `event_id`、`date`、`kind`、`summary`、`source`。ID 使用小写英文、数字和连字符；`date` 是实际事件发生日，格式为 `YYYY-MM-DD`。脚本首次保存时自动增加 UTC 写入时间 `recorded_at`，不改变原发生日期；同一数据目录在时钟精度不足或回拨时按微秒递增，保持写入先后。输入无需填写 `recorded_at`，即使传入也忽略，重复提交保留第一次写入时间。`kind` 为非空文本，建议 `discussion`、`exploration`、`attempt`、`context_update`、`preference`、`correction`、`review` 或 `follow_up`。类型只表达事件用途，不决定证据强度。

```json
{
  "event_id": "event-example-01",
  "date": "2026-10-04",
  "kind": "exploration",
  "summary": "本题目前形成的理解和仍待验证的选择，示例需替换为本轮事实",
  "source": "实际文件与位置，或本次会话日期和用户原话定位",
  "case_id": "case-example",
  "context_ref": "project-example",
  "user_contribution": "用户本轮实际提出的判断或材料，没有则省略",
  "assistance": "导师示范、专家建议或其他获得的帮助",
  "unresolved": "尚未解决的问题",
  "next_step": "双方明确的下一步；没有约定则省略",
  "preferences": ["仅保存用户明确表达且有来源的偏好"]
}
```

可选 `case_id`、`context_ref` 未知时省略；其余可选文字字段为字符串，`preferences` 为字符串数组。更正事件增加 `corrections` 数组，每项为 `{"event_id":"原事件ID","reason":"更正内容与理由"}`，原事件须已存在；更正旧人工记录可用 `{"record_ref":"growth-log.md 中实际日期和标题","reason":"更正内容与理由"}`。一项只用一种目标，当前事件的 `source` 给出更正来源。更正不覆盖原事件，也不自动修改案例、能力观察或背景快照；主导师核对后同步相关当前状态，并在记录中说明受影响的位置。

脚本在同一数据目录的 `.pm-grow.lock` 下写入，每条事件原子保存后读回。相同 ID 与相同内容重复提交不会新增；内容不同会明确报错，应使用新 ID 追加更正。`growth-log.md` 的 `pm-grow:events:start/end` 区域是派生索引，脚本保留区域外原有人工文字。进程在事件保存后中断时，可以原样重试或执行 `rebuild-log` 修复索引，不删除已保存事件。手工更新共享目录也需遵守同一锁或先协调单一写入者。默认锁等待 10 秒，可在子命令前加 `--lock-timeout <秒数>`；超时后报错，不绕开锁。

## 案例与尝试

从 [case.json](../templates/case.json) 建立案例。一个真实任务或独立模拟题只使用一个 case_id，后续轮次、修订、不同能力观察加入同一案例。无关的新任务使用新 ID。

案例可选填 `context_ref`，指向稳定的业务或项目上下文；`context_snapshot` 保留当时的 `project`、`role`、`constraints`（字符串数组）和 `help_received`。每次比较成长都核对当时职责、约束和获得帮助，不能把当前背景倒填成过去事实。旧案例缺这些字段仍兼容；未知内容留空并标明未确认。业务背景更新不直接改写历史快照，发现历史记录错误时追加有来源的更正，再由主导师修正受影响的快照。

每次尝试记录用户自己的内容或原话、日期、来源定位、获得的帮助、反馈和实际结果：

- kind：`independent`、`guided`、`model_demo`、`acknowledgement`。
- status：`active`、`withdrawn`、`unverified`。
- source：真实文件与位置，或会话日期和用户原话定位；不能只引用模型自己的总结。
- user_work：用户实际判断或产出摘要。模型示范和只说理解了不冒充独立产出。
- observations：能力 ID、具体观察、状态及理由。撤回诊断可以只撤回对应观察，不抹除有效的用户尝试。

语义判断仍由导师核对。脚本只检查格式与计数，不证明证据真实或能力达标。

## 扩展能力

八项底座之外确有训练需要时，由主导师在本学习者的 `abilities.json` 注册 `custom.<slug>` 能力，说明名称、边界和可观察行为，再在案例 `ability_ids` 或观察中引用。单个定义输入格式为 `{"id":"custom.example","name":"名称","definition":"定义与适用边界","observable_behaviors":["可观察行为"]}`。

```sh
python3 <skill-dir>/scripts/state.py --data-dir <data-dir> register-ability --input <ability.json>
```

注册表格式为 `{"schema_version":1,"abilities":[定义对象]}`。相同定义重复注册保持幂等；同 ID 内容变化须核对旧含义及相关证据后使用 `--replace`。替换时脚本在可选 history 数组记录 `replaced_at`、`ability_id` 和完整 `previous_definition`，旧文件没有 history 仍兼容。含义已改变的能力应新建 ID，避免旧证据被重新解释。专家提出的新维度只是建议，注册与评价仍由主导师负责。扩展能力不增加案例数量，也不自动改变已核实的能力状态。

## 独立案例计数

回顾候选案例需同时满足：

1. owner 为 self，status 为 closed，origin 为 work 或 simulation。
2. 至少一次 active 的 independent 或 guided 尝试，且有实际 user_work 和 source。
3. 本次回顾周期尚未覆盖该 case_id。

一份产出的多个错误或多个能力标签只算一个案例。重复 case_id 视为数据错误。纯示范、认同、讨论、第三方、未核实历史记录、纠错条目不计数。模拟练习可作为用户实际尝试，但不可据此证明真实业务效果。

查看状态达到三个新案例后，在自然收尾主动回顾。回顾完成并实际写入账本后，再标记对应 ID：

```sh
python3 <skill-dir>/scripts/state.py --data-dir <data-dir> mark-reviewed --case-id <id-1> --case-id <id-2> --case-id <id-3>
python3 <skill-dir>/scripts/state.py --data-dir <data-dir> defer-review
```

用户暂缓后，证据未变化前不重复触发；新增相关材料或用户主动要求时可接续。已回顾案例的后续变化仍可用于局部迁移验证，但不能伪造新 ID 再充数。

## 观察不等于能力结论

记录可从具体观察开始。候选观察、得到支持的局部判断、被反证撤回分开管理。稳定模式需要跨独立案例的可比证据并排除信息缺失等替代解释；三个案例只触发回顾，不自动确认缺口或升级。

训练主题可由用户主动选择或当前任务价值决定，无需凑够缺口证据。学习计划区分“主动练习”“局部观察待验证”“反复模式需继续核对”。

更正时追加更正事件及目标记录，保留历史原文、原日期和原来源；主导师更新当前计划与快照，撤回无效观察。原始记录以后结合更正后的有效状态解释。脚本只保留关联与验证存储，不自动完成能力评价或快照校正。

## 写入纪律与旧版兼容

- 数据目录锁保护同一文件系统中遵守该锁的写入进程，不提供跨机器文件副本的分布式同步。共享副本时应协调写入并检查冲突。
- 日期使用实际绝对日期；记录有实质变化的本人学习交流，包括探索、未完成方案、背景变化、偏好与纠错，不把技能安装或普通制图计为成长。
- 先读取当前文件再小范围更新，保留不相关内容。多端共享时发现内容已变，重新读取后合并，避免整份旧快照覆盖。
- 写完读回核对再说已记录。初始化、邀请、回顾标记等操作本身不等于训练完成。
- v0.3 的标题条数不再作为回顾证据数量。旧记录未逐项核对原始用户产出前，保持 legacy/unverified，不自动转换成合格案例。
- v1.0 人工 Markdown 和案例继续可读；没有 events/、abilities.json 或可选上下文字段时，不视为档案损坏，不为了读取而初始化，也不批量伪造日常事件。
- 旧能力名称与新 ID 明确映射：旧数据与决策对应 data_validation，旧方案与产品设计对应 solution_design；其余按名称校准。旧整体 L 等级保留为历史，不自动提升当前状态。
