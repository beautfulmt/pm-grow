# PRD 写作

## 解决什么问题

PRD 是团队对"做什么、为什么做、做到什么程度"的共同参照。好的 PRD 让读者快速理解问题和目标，让设计、研发、测试、运营各取所需，并保留决策记录。写的过程本身也是 PM 检查思考是否完整的手段。

## 核心步骤

1. **先写一页摘要**：背景与问题、目标用户、目标与衡量指标、范围（做与不做）、关键决策与待决事项。
2. **问题与证据**：链接问题陈述和数据、访谈依据（见[问题界定](problem-framing.md)）。
3. **方案概述**：主流程、关键页面或交互、与现有系统的关系，附原型或流程图。
4. **详细规则**：业务规则表、[流程与状态设计](flow-state.md)、权限、数据字段、异常与边界、文案。
5. **验收标准**：按[用户故事与验收标准](user-story.md)或功能点列出。
6. **非功能需求**：性能、安全、合规、埋点、兼容性。
7. **上线与运营**：灰度、监控指标、回滚条件、运营和客服准备（见[发布与灰度](launch-rollout.md)）。
8. **变更记录与待决问题**：谁在什么时候决定了什么。

写完自查：一位新加入的研发只读这份文档，能否回答"为什么做、做完怎么判断成功、哪些情况要特殊处理"。

## 适用条件

- **适合**：需要多角色协作、规则较多、需要长期留档的需求。
- **前提**：问题、目标和范围已与关键相关方初步对齐。
- **换用或简化**：团队小、沟通紧密时，用一页纸摘要 + 用户故事 + 原型替代；合规或审计要求高的业务需要更完整的文档。

## 误用与反例

- 一上来就写页面细节 → 先写问题、目标和范围，再写方案。
- 写成一次交付的合同 → 当作活文档，记录变更和决策。
- 只写正常流程 → 规则和异常部分往往决定质量，花足时间。
- 目标写成"提升用户体验" → 写成可衡量的指标和判断标准。
- 篇幅过长没人读 → 摘要放最前，详细规则用表格和附件分层。

## 行业变形

- [金融科技](../industries/fintech.md)、[医疗健康](../industries/healthcare.md)：附上合规评审结论、审计要求和数据处理说明。
- [游戏](../industries/gaming.md)：玩法以策划案和数值表为主，PRD 侧重系统、商业化和运营活动。
- [AI 产品](../industries/ai-product.md)：增加评测集、效果标准、失败处理、人工兜底和成本预算。
- [硬件/IoT/工业制造](../industries/hardware-iot.md)：硬件规格与软件、固件需求分开写，标明不可更改的时间点。

## 不同阶段怎么用

- **newcomer 新人**：照着用。按团队模板写，先把摘要给导师和研发看，对齐后再展开细节。
- **independent_pm 独立 PM**：会选会改。按需求复杂度调整文档深度，用 PRD 推动评审和决策。
- **senior 资深**：判断何时少写、何时多写，把精力放在关键规则和决策记录上；指导他人改进文档。
- **expert 专家**：输出本领域的规则与验收标准附录，供团队复用。
- **lead 负责人**：设定团队的文档标准和评审流程，控制文档成本。
