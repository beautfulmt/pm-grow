# 发布与灰度

## 解决什么问题

上线是风险集中的时刻：功能缺陷、性能问题、用户不适应、运营没准备好、指标意外下降。发布与灰度把上线变成可控的过程：先小范围、可监控、可回滚，再逐步扩大，同时让相关方和用户提前准备好。

## 核心步骤

1. **上线准备清单**：功能验收、性能与安全、埋点与看板、客服和运营材料、对外说明、合规确认。
2. **灰度方案**：内部员工 → 小比例用户 → 特定人群或地区 → 全量，逐步放开；用功能开关（feature flag）控制范围。
3. **监控与判定标准**：技术指标（错误率、延迟、崩溃）和业务指标、护栏（转化、投诉、退款）；每一阶段写清继续、暂停、回滚的条件。
4. **回滚预案**：能否快速关闭开关、数据变更是否可逆、不可逆部分如何补偿。
5. **沟通计划**：研发、运营、客服、销售分别在什么时候知道什么；对外用户的通知和引导。
6. **执行与值守**：上线窗口避开流量高峰和关键业务时段，安排值守人员和升级路径。
7. **上线回看**：按约定的时间点回看指标和反馈，确认问题是否真正解决，再进入[复盘](retrospective.md)。

## 适用条件

- **适合**：所有面向用户的变更，力度与风险相称。
- **前提**：具备基本的开关、监控和回滚能力；缺失时在上线计划中写明替代措施。
- **换用或简化**：小改动简化为开关 + 监控 + 回看时间；大改版、资金相关、不可逆的变更需要完整方案，并结合[风险清单与预案](risk-register.md)。

## 误用与反例

- 一次性全量上线 → 有条件时先灰度。
- 灰度没有判定标准 → 每个阶段写清继续和回滚条件。
- 只看技术指标 → 同时看业务护栏和用户反馈。
- 上线即结束 → 约定回看时间，确认问题是否解决。
- 客服和运营在上线当天才知道 → 提前同步并准备话术。

## 行业变形

- [硬件/IoT/工业制造](../industries/hardware-iot.md)：固件升级分批推送，支持断点续传和失败恢复，回滚成本高。
- [企业服务 SaaS](../industries/saas.md)：重大变更提前通知客户管理员，部分客户需要可选开关或延后升级。
- [游戏](../industries/gaming.md)：版本更新集中，玩家对改动敏感，提前公告并准备补偿机制。
- [金融科技](../industries/fintech.md)：资金相关变更用对账验证，灰度要保证交易一致性。
- [教育](../industries/education.md)：避开考试周和开学首周，提前培训教师。

## 不同阶段怎么用

- **newcomer 新人**：照着用。按清单准备一次小功能上线，写出监控指标和回滚条件。
- **independent_pm 独立 PM**：会选会改。设计灰度节奏和判定标准，协调各方完成上线，并主持回看。
- **senior 资深**：按风险调整上线策略，处理上线中的异常和艰难决策（回滚还是热修复）。
- **expert 专家**：沉淀本领域的发布规范和检查清单。
- **lead 负责人**：建立发布纪律和值守机制，平衡交付速度与稳定性。
