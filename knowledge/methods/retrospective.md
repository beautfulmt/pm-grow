# 复盘（GRAI/AAR）

## 解决什么问题

经历不会自动变成能力。复盘通过回顾目标、对比结果、分析原因、提炼规律，把一次项目或决策的经验变成下次可用的判断和做法，关注的是改进而不是追责。PM 的成长大多来自对真实任务的复盘，导师判断"方法是否迁移"也依赖复盘留下的记录。

## 核心步骤

以联想复盘的四步（GRAI）为主线，融入美军事后回顾（AAR）的提问：

1. **回顾目标（Goal）**：当初想达成什么？成功标准是什么？原本预期会发生什么？
2. **评估结果（Result）**：实际发生了什么？和目标相比，差距和亮点各在哪里？用数据和事实说话。
3. **分析原因（Analysis）**：差距和亮点为什么出现？区分可控与不可控、判断失误与执行失误、运气与能力；还原当时掌握了哪些信息。
4. **总结规律（Insight）**：提炼可迁移的经验：在什么条件下应该怎么做；写清下次要保持、开始、停止做的事。
5. **落实行动**：每条经验对应具体的改进动作、负责人和时间；需要时更新流程或方法卡。
6. **检验迁移**：在后续任务中有意识地用上，下次复盘时检查它是否奏效。

团队复盘前先共同认同：每个人都是在当时的信息、技能和资源下尽了最大努力。这让讨论聚焦在系统和决策过程上，大家才愿意坦诚。

## 适用条件

- **适合**：上线后、关键决策出结果后、阶段结束、重大事故后；也适合个人对一周工作或一次沟通做小复盘。
- **前提**：有当初的目标或预期可以对照；没有时先还原当时的判断。
- **换用或简化**：结果尚未出现时，先复盘决策过程；个人小复盘只回答四个问题即可。

## 误用与反例

- 开成追责会 → 聚焦系统和决策过程，而不是个人过错。
- 用结果好坏评判决策好坏 → 区分决策质量和运气。
- 结论太泛（"沟通要加强"）→ 写成具体条件和做法。
- 复盘完没有行动、之后也不再检查 → 每条经验对应动作，下次复盘时回看。

## 行业变形

- [教育](../industries/education.md)：效果周期长，按学期节点分段复盘，结合过程指标。
- [游戏](../industries/gaming.md)：版本或活动结束后复盘，结合玩家反馈和数据。
- [硬件/IoT/工业制造](../industries/hardware-iot.md)：在产品代际之间复盘，经验沉淀到下一代的规格和流程。
- [AI 产品](../industries/ai-product.md)：把失败样例纳入评测集，成为长期资产。

## 不同阶段怎么用

- **newcomer 新人**：照着用。每完成一项任务按四问写一段复盘，导师重点帮助区分事实和解读。
- **independent_pm 独立 PM**：会选会改。主持团队复盘，提炼可迁移的经验并落到流程里。
- **senior 资深**：识别跨项目反复出现的模式，判断经验的适用边界。
- **expert 专家**：把复盘得出的规律沉淀为领域方法和标准。
- **lead 负责人**：建立组织的复盘机制和心理安全，让经验在团队之间流动。
