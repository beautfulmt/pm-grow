# 流程与状态设计

## 解决什么问题

功能说明常写清了"正常怎么走"，却漏掉中断、重试、撤销、超时、并发和权限变化，而这些正是线上问题和客诉的主要来源。流程图描述"谁在什么条件下做什么、接下来到哪"，状态机描述"一个对象有哪些状态、由什么事件触发转换"。两者结合，可以系统地覆盖边界情况。

## 核心步骤

1. **找核心对象**：订单、工单、课程、申请、设备……列出它在业务中的生命周期。
2. **列状态**：用业务语言命名，状态之间互斥且含义明确；标出初始状态和终止状态。
3. **列事件与转换**：哪个角色或系统事件触发哪个转换、前置条件是什么、转换时产生什么副作用（通知、扣款、写日志）。
4. **画状态转换表**：行是当前状态，列是事件，格子里填目标状态或"不允许"，逐格检查。
5. **画主流程和泳道**：按角色画正常路径，再补异常分支：失败、超时、取消、回退、重复提交。
6. **检查边界**：并发操作、网络中断、权限变化、数据缺失、跨系统不一致时怎么处理；每个页面的空、加载中、出错、无权限状态。
7. **与研发、测试走查**：把转换表作为测试用例的来源。

## 适用条件

- **适合**：有生命周期的业务对象、多角色协作、涉及资金或履约、跨系统交互的需求。
- **前提**：业务规则有明确的来源（制度、合同、产品决策），拿不准的规则先列为待确认。
- **换用或简化**：纯展示页面只检查页面状态；概念本身混乱时，先做[领域建模](domain-modeling.md)。

## 误用与反例

- 只画正常路径 → 每个节点都问"失败了怎么办、用户反悔怎么办"。
- 业务状态和前端展示文案混用 → 分开定义，再给出两者的映射。
- 转换规则散落在 PRD 各处 → 汇总成一张转换表。
- 只写允许的转换 → 写明哪些操作在某状态下被禁止，以及对用户的提示。

## 行业变形

- [电商与零售](../industries/ecommerce.md)：订单、支付、物流、售后多个状态机互相关联，部分发货和部分退款最易出错。
- [本地生活/出行/O2O](../industries/local-services.md)：履约状态实时变化，超时、改派、取消的责任归属需要明确规则。
- [金融科技](../industries/fintech.md)：资金状态必须一致、可对账，任何中间态都要有补偿或人工处理路径。
- [硬件/IoT/工业制造](../industries/hardware-iot.md)：设备在线、离线、固件升级、配网失败等状态要考虑弱网和断电。
- [中后台与内部系统](../industries/internal-platform.md)：审批流的退回、转交、加签、撤回、超时是高频遗漏。

## 不同阶段怎么用

- **newcomer 新人**：照着用。为一个对象画状态转换表，导师检查异常分支和"不允许"的格子是否覆盖。
- **independent_pm 独立 PM**：会选会改。主动识别需要状态机的需求，和研发对齐边界处理。
- **senior 资深**：判断复杂度值得投入多少设计，优先验证风险高的转换；处理跨系统一致性方案。
- **expert 专家**：维护本领域核心对象的标准状态模型，与领域模型保持一致。
- **lead 负责人**：推动核心对象的状态在各团队间统一定义，减少系统割裂。
