# 用户故事与验收标准

## 解决什么问题

需求从 PM 传到设计、研发和测试时容易失真。用户故事用"谁、想做什么、为了什么"描述一段用户价值，配合验收标准划清完成的边界，让团队围绕用户结果讨论实现，也为测试和验收提供依据。用户故事地图再把故事按用户活动排开，帮助看全局和切版本。

## 核心步骤

1. **写故事**："作为<角色>，我想<行为>，以便<价值>。"角色要具体，价值要是用户感知得到的结果。
2. **补验收标准**：用"假如<前提>，当<动作>，那么<结果>"（Given/When/Then）写出正常、边界、异常三类情况。
3. **用 INVEST 检查**：独立、可协商、有价值、可估算、足够小、可测试。过大的故事按流程步骤、数据范围、角色或规则拆开。
4. **三方对话确认**：卡片（Card）只是提醒，关键在对话（Conversation）和确认（Confirmation）：和设计、研发、测试一起走一遍，补上遗漏的状态和规则。
5. **画故事地图**：横轴是用户活动和步骤，纵轴是细节和优先级；横切一条线，定义首个可用版本（见[MVP 切片](mvp-slicing.md)）。
6. **随变更维护**：需求变化时同步更新验收标准，验收时逐条对照。

## 适用条件

- **适合**：敏捷团队的需求表达和拆分，尤其是需要多人协作理解的功能。
- **前提**：问题和目标已经清楚（见[问题界定](problem-framing.md)），团队能当面或线上对话澄清。
- **换用或简化**：规则密集或强监管的场景，故事之外还需要规则表和[流程与状态设计](flow-state.md)；纯技术改造用任务描述即可。

## 误用与反例

- "作为用户，我想要一个按钮" → 写出具体角色和要达成的结果。
- 只有故事没有验收标准 → 至少写一个正常、一个边界、一个异常情况。
- 按技术层拆（前端一张、后端一张）→ 按用户可感知的价值纵向拆分。
- 当成一次写死的合同 → 通过对话澄清，随理解加深而更新。

## 行业变形

- [金融科技](../industries/fintech.md)：验收标准覆盖资金一致性、幂等、对账、异常重试和审计留痕。
- [中后台与内部系统](../industries/internal-platform.md)：角色多、权限细，故事注明角色与权限，验收覆盖越权场景。
- [游戏](../industries/gaming.md)：玩法通常用策划案和数值表表达，用户故事更适合系统与商业化功能。
- [AI 产品](../industries/ai-product.md)：验收标准改为评测集上的通过要求、失败样例的处理方式和人工兜底。

## 不同阶段怎么用

- **newcomer 新人**：照着用。按模板写故事和验收标准，导师检查角色、价值和异常情况是否齐全。
- **independent_pm 独立 PM**：会选会改。合理拆分故事，和研发、测试高效对齐，用故事地图规划版本。
- **senior 资深**：判断何时故事就够、何时需要更完整的规则文档，帮助团队提升需求质量。
- **expert 专家**：沉淀本领域通用的验收标准清单（如资金、权限、合规）。
- **lead 负责人**：设定团队的需求就绪标准，平衡文档成本和协作质量。
