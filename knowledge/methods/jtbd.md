# 待办任务（JTBD）

## 解决什么问题

用户在特定情境下"雇用"产品来取得某种进展。JTBD 把注意力从人口属性和功能清单移到"情境 + 想取得的进展 + 判断好坏的标准"，用来解释用户为什么开始用、为什么换掉、为什么放弃，并找出真正的竞争对手：包括 Excel、找人帮忙、什么都不做这类非产品的替代做法。

## 核心步骤

1. **选对访谈对象**：找最近真正做过"切换"的人：刚开始用、刚放弃、刚换到别家。
2. **还原时间线**：从第一次冒出念头开始，经过被动留意、主动寻找、做决定，到用了之后。每一段追问具体时间、地点、当时在用什么。
3. **识别四种力量**：现状的推力、新方案的拉力、对新方案的焦虑、对旧习惯的依恋。
4. **写任务陈述**："当<情境>时，我想<取得的进展>，以便<期望结果>。"分别检查功能、情感、社交三个维度。
5. **列替代方案**：用户此刻"雇用"的所有做法，含手工、外包、凑合和放弃。
6. **提炼衡量标准**：用户判断这件事做得好的标准（如"尽量缩短找到某信息的时间"），作为方案设计和指标的依据。
7. **回到产品**：哪些推力和拉力可以放大，哪些焦虑和依恋需要降低。

## 适用条件

- **适合**：新方向探索、增长瓶颈、流失分析、定位和竞争范围界定。
- **前提**：能找到近期发生过选择行为的真实用户。
- **换用或简化**：强制使用的场景（如内部系统）里"切换"不明显，改为观察用户绕过系统的做法；只需快速改写一条需求时，写任务陈述那一步就够。

## 误用与反例

- 任务写成功能（"我想要一个筛选器"）→ 退回情境和进展（"周一开会前，我想快速确认上周哪些门店异常"）。
- 只问"你需要什么" → 改问"上一次你这么做是什么时候，当时发生了什么"。
- 一个任务覆盖所有人 → 按情境拆开，不同情境的任务和竞争对手不同。
- 用任务陈述代替验证 → 任务假设仍要用行为数据或实验检验。

## 行业变形

- [教育](../industries/education.md)：家长要的进展常是安心和看得见的进步，学生要的是完成作业或通过考试，分开写。
- [企业服务 SaaS](../industries/saas.md)：组织任务（降本、合规）和个人任务（少加班、对上有交代）同时存在。
- [电商与零售](../industries/ecommerce.md)：同一商品在送礼、自用、囤货情境下任务不同，影响详情页和推荐。
- [内容/社区/社交](../industries/content-community.md)：情感与社交维度常是主任务，功能维度反而次要。
- [广告与商业化](../industries/ads-monetization.md)：品牌广告主和效果广告主雇用平台的任务不同。
- [开发者与工具类产品](../industries/developer-tools.md)：开发者雇用工具是为了更快、更可靠地交付自己的产品，替代方案常是自己写或用开源方案。

## 不同阶段怎么用

- **newcomer 新人**：照着用。用任务陈述模板改写一条需求，再找一位最近切换过的用户做一次时间线访谈。
- **independent_pm 独立 PM**：会选会改。能用四种力量解释一次转化或流失，并据此提出方案假设。
- **senior 资深**：判断何时用 JTBD（新方向、定位），何时用更轻的方法；能识别任务写得过宽导致的空洞结论。
- **expert 专家**：为本领域建立任务地图和衡量标准清单，供团队复用。
- **lead 负责人**：用任务划定产品边界和团队分工，让团队围绕任务而不是功能组织。
